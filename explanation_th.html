1. ภาพรวมระบบและโจทย์ที่ได้รับ

ระบบ Identity & Academic Core - Timetable & Room พัฒนาขึ้นเพื่อแก้ปัญหาความผิดพลาดในการจัดตารางเรียนและห้องเรียนในระดับมหาวิทยาลัย ซึ่งเดิมใช้โปรแกรมตารางคำนวณ (Spreadsheets) ทำให้เกิดปัญหาการจองห้องชนกัน (Double-booking) และนักศึกษาเข้าเรียนเกินความจุห้อง

ผู้ใช้งานหลัก 2 กลุ่ม:

  1. Student (นักศึกษา): เข้ามาดูตารางเรียนรายสัปดาห์ของตนเอง (คำนวณจากวิชาที่ลงทะเบียนไว้โดยอัตโนมัติ) และดูตารางการใช้งานห้องเรียนต่างๆ ได้แบบอ่านอย่างเดียว (Read-only)
  2. Staff / Room Planner (เจ้าหน้าที่จัดตาราง): มีสิทธิ์ในการจัดคลาสเรียนลงห้องและเวลา (Create, Update, Delete Meetings) โดยมีระบบตรวจสอบความขัดแย้งอัตโนมัติคอยป้องกันไม่ให้เกิดข้อผิดพลาด

2. ทำไมต้อง Cloudflare D1 แทนที่จะเป็น Firebase Firestore?

ในการออกแบบระบบจริง ทีมงานได้วิเคราะห์ข้อจำกัดของ NoSQL (Firestore) เทียบกับ Relational SQL (Cloudflare D1) และพบว่า Cloudflare D1 เหมาะสมกับงานจัดตารางห้องเรียนมากกว่าในทุกมิติ:

ประเด็นการเปรียบเทียบ Google Cloud Firestore (NoSQL) Cloudflare D1 (Serverless Relational SQLite) ผลกระทบต่อระบบ Timetable & Room
ความถูกต้องของข้อมูล (Relational Integrity) ไม่มี Foreign Key ถ้ามีการลบห้องเรียน ข้อมูลการจัดตาราง (Meetings) จะกลายเป็นข้อมูลขยะค้างอยู่ในระบบ มี Foreign Key Constraints แท้จริง รองรับ ON DELETE RESTRICT D1 เหนือกว่า: ฐานข้อมูลจะบล็อกการลบห้องเรียนที่มีคลาสเรียนผูกอยู่ทันทีในระดับ Database Engine
การตรวจจับเวลาชนกัน (Time Overlap Query) ไม่สามารถ Query ช่วงเวลาคร่อมกัน 2 ตัวแปรข้ามหลายฟิลด์ได้ง่าย ต้องดึงข้อมูลทั้งหมดมาวน Loop เช็คในแอปพลิเคชัน ใช้ SQL เช็คช่วงเวลาเหลื่อมกันได้โดยตรง (start < new_end) AND (end > new_start) D1 เหนือกว่า: ค้นหาและตรวจจับเวลาชนกันผ่าน B-Tree Index จบในเวลาเพียง 0.18 ms
การป้องกันการแย่งจองห้อง (Race Conditions) ต้องเขียน Transaction ซับซ้อน และเสี่ยงต่อการ Retry เมื่อมีผู้ใช้งานพร้อมกัน รองรับ ACID Transactions แท้จริงในระดับ SQLite D1 เหนือกว่า: ป้องกันการเกิด Double-booking จากการกดบันทึกพร้อมกันได้อย่างสมบูรณ์แบบ 100%
ความเร็วในการตอบสนอง (Latency & Cold Start) Cloud Functions มีปัญหา Cold Start (ต้องรอเริ่มระบบ 1 - 3 วินาที) Cloudflare Workers ทำงานบน V8 Isolate เริ่มทำงานใน 2 ms (ไม่มี Cold Start) D1 เหนือกว่า: นักศึกษาเปิดดูตารางเรียนได้รวดเร็วทันใจ โหลดข้อมูลเสร็จในเสี้ยววินาที
โควต้าการใช้งานฟรี (Free Tier - งบ 0 บาท) อ่านฟรี 50,000 ครั้ง/วัน อ่านฟรี 5,000,000 ครั้ง/วัน (มากกว่า 100 เท่า) เขียนฟรี 100,000 ครั้ง/วัน D1 เหนือกว่า: รองรับช่วงเวลาลงทะเบียนที่มีผู้ใช้งานเปิดดูตารางเรียนพร้อมกันจำนวนมหาศาลโดยไม่มีค่าใช้จ่าย

3. การออกแบบฐานข้อมูล (Database Schema & Constraints)

ฐานข้อมูลประกอบด้วย 6 ตารางหลักที่เชื่อมโยงกันอย่างรัดกุม:

[users] ──(ลงทะเบียน)──> [enrollments] <──(ผูกกลุ่มเรียน)── [sections] <── [courses]
  │                                                            │
  │ (ผู้จัดตาราง)                                                │ (คลาสเรียน)
  ▼                                                            ▼
[meetings] <─────────────────────────────────────────────── [rooms]

รายละเอียดโครงสร้างตาราง:

  1. users (ผู้ใช้งาน):
    • ฟิลด์: id (PK), name, email (UNIQUE), role (student หรือ staff), department
    • หน้าที่: แยกสิทธิ์การใช้งานระหว่างนักศึกษาและเจ้าหน้าที่
  2. rooms (ห้องเรียน):
    • ฟิลด์: id (PK), name (UNIQUE เช่น C1-101), building, capacity (จำนวนที่นั่ง), room_type (lecture, lab, seminar), status
    • Constraint: CHECK(capacity > 0) ป้องกันการใส่ความจุติดลบ
  3. courses (หลักสูตร/รายวิชา):
    • ฟิลด์: id (PK), course_code (UNIQUE เช่น SWE204), course_name, department, credits
  4. sections (กลุ่มเรียน):
    • ฟิลด์: id (PK), course_id (FK เชื่อมไปที่ courses.id), section_number, capacity, semester, academic_year, enrolled_count
    • Constraint: ป้องกันการสร้างกลุ่มเรียนซ้ำในภาคเรียนเดียวกันด้วย UNIQUE(course_id, section_number, semester, academic_year)
  5. meetings (ตารางการใช้ห้องเรียน - ตารางหัวใจสำคัญ):
    • ฟิลด์: id (PK), section_id (FK), room_id (FK), day_of_week (จันทร์-อาทิตย์), start_time, end_time, status
    • Constraint 1: CHECK(start_time < end_time) ป้องกันเวลาเริ่มมากกว่าเวลาเลิก
    • Constraint 2: room_id REFERENCES rooms(id) ON DELETE RESTRICT ป้องกันการลบห้องเรียนที่มีการใช้งานอยู่
  6. enrollments (การลงทะเบียนเรียน):
    • ฟิลด์: id (PK), student_id (FK), section_id (FK), status
    • Constraint: UNIQUE(student_id, section_id) ป้องกันนักศึกษาลงทะเบียนในกลุ่มเรียนเดิมซ้ำ

4. กฎทางธุรกิจ (Business Rules) และการป้องกันข้อผิดพลาด

ในโค้ด Backend API (src/routes/meetings.ts) มีการบังคับใช้กฎตาม PRD อย่างเข้มงวด:

กฎข้อที่ 1: BR-01 ป้องกันเวลาเรียนทับซ้อนในห้องเดียวกัน (Overlap Prevention)

เมื่อเจ้าหน้าที่ต้องการสร้างหรือแก้ไขการจัดตาราง ระบบจะคำนวณช่วงเวลาเหลื่อมกันทางคณิตศาสตร์: $$\text{Interval 1 } [s_1, e_1) \quad \text{ชนกับ} \quad \text{Interval 2 } [s_2, e_2) \iff (s_1 < e_2) \land (e_1 > s_2)$$

โค้ด SQL ที่ระบบใช้ตรวจสอบ:

SELECT m.id, m.start_time, m.end_time, c.course_code, s.section_number
FROM meetings m
JOIN sections s ON m.section_id = s.id
JOIN courses c ON s.course_id = c.id
WHERE m.room_id = ?
  AND m.day_of_week = ?
  AND m.status = 'active'
  AND m.start_time < ?  -- เวลาเริ่มเดิม ต้องมาก่อนเวลาเลิกใหม่
  AND m.end_time > ?    -- เวลาเลิกเดิม ต้องหลังเวลาเริ่มใหม่
LIMIT 1;
  • หากพบว่าเวลาชนกัน ระบบจะปฏิเสธการบันทึกทันที พร้อมส่ง HTTP 409 Conflict และบอกว่าชนกับวิชาอะไร เวลาไหน

กฎข้อที่ 2: BR-02 ป้องกันจำนวนนักศึกษาเกินความจุห้อง (Capacity Check)

ก่อนบันทึก ระบบจะเปรียบเทียบ: $$\text{section.capacity} \le \text{room.capacity}$$

  • หาก Section มีนักศึกษา 50 คน แต่ห้องจุได้ 35 ที่นั่ง ระบบจะปฏิเสธการบันทึกทันที พร้อมส่ง HTTP 400 Bad Request

กฎข้อที่ 3: BR-05 ระบบแนะนำช่วงเวลาว่างทดแทน (Deterministic Scan Fallback)

ที่ Endpoint POST /api/conflicts/check หากเวลาที่ส่งมาชนกับคลาสอื่น ระบบจะสแกนหาช่วงเวลามาตรฐานที่ห้องนั้นยังว่างอยู่ในวันเดียวกัน (เช่น 13:00-15:00 หรือ 15:00-17:00) และส่งเป็นรายการคำแนะนำกลับไปให้เจ้าหน้าที่เลือกใช้ได้ทันที

5. สถาปัตยกรรม Backend API (Cloudflare Workers + Hono)

ระบบ Backend สร้างขึ้นด้วยเทคโนโลยี Edge สมัยใหม่:

  • Cloudflare Workers: ทำหน้าที่เป็น Serverless Compute รันอยู่บนโหนดเครือข่ายของ Cloudflare กว่า 300 เมืองทั่วโลก (สำหรับผู้ใช้ในไทยจะรันที่กรุงเทพฯ BKK PoP โดยตรง ทำให้มี Latency ต่ำมาก)
  • Hono Framework: เป็น Web Framework สำหรับ Edge ที่มีขนาดเบามาก (~300 KB) รองรับ Routing แบบ Type-safe
  • D1 Binding (c.env.DB): เป็นการเชื่อมต่อฐานข้อมูล SQLite ภายใน Worker Process โดยตรง โดยไม่ต้องต่อผ่าน TCP Connection Pool ให้เกิด Overhead

6. การเชื่อมต่อและ Deploy สู่ Cloudflare จริง

ระบบนี้ไม่ได้รันจำลองเฉพาะในเครื่อง แต่ได้ Deploy ขึ้นระบบ Production บน Cloudflare จริงเรียบร้อยแล้ว:

  1. การสร้างฐานข้อมูล:
    npx wrangler d1 create timetable-room-db
  2. การรัน Schema Migration สู่ Remote Cloudflare:
    npx wrangler d1 execute timetable-room-db --remote --file=./migrations/0001_initial_schema.sql -y
  3. การใส่ข้อมูลเริ่มต้น (Seed Data) สู่ Remote Cloudflare:
    npx wrangler d1 execute timetable-room-db --remote --file=./migrations/0002_seed_data.sql -y
  4. การ Deploy Worker API:
    npx wrangler deploy
    URL ที่ใช้งานได้จริง: https://timetable-room-api.6731503021.workers.dev

8. แนวทางการตอบคำถามอาจารย์ (Q&A Presentation Prep)

Q1: ทำไมถึงเปลี่ยนจาก Firestore ใน PRD เดิมมาเป็น Cloudflare D1?

ตอบ: เพราะปัญหาหลักของระบบ Timetable & Room คือ "ความสัมพันธ์ของข้อมูล" และ "การป้องกันการจองห้องชนกัน" Firestore เป็น NoSQL ไม่มี Foreign Key ทำให้ข้อมูลเสี่ยงเป็นขยะเมื่อมีการลบห้อง และไม่สามารถ Query เช็คช่วงเวลาเหลื่อมกันได้ง่าย แต่ Cloudflare D1 เป็น Relational SQL มีทั้ง Foreign Key, Check Constraints และ ACID Transactions ที่ช่วยดักจับข้อผิดพลาดตั้งแต่ระดับ Database Engine แถมยังมีความเร็วระดับ Edge (0ms cold start) และโควต้าฟรี 5 ล้านครั้ง/วัน

Q2: ระบบรู้ได้อย่างไรว่าห้องเรียนถูกจองเวลาซ้อนกัน? (BR-01)

ตอบ: ระบบใช้เงื่อนไขตรวจสอบช่วงเวลาทางคณิตศาสตร์ (start_time < new_end) AND (end_time > new_start) ค้นหาในห้องเดียวกันและวันเดียวกัน หากพบว่ามีคลาสเรียนที่ยัง Active อยู่ ระบบจะไม่อนุญาตให้บันทึก และส่ง HTTP Status 409 Conflict พร้อมรายละเอียดของคลาสที่ชนกันกลับไป

Q3: นักศึกษาดึงตารางเรียนของตนเองได้อย่างไร?

ตอบ: ผ่าน Endpoint GET /api/timetables/me?student_id=... โดยระบบจะทำการ JOIN ตาราง enrollments เข้ากับ sections, courses, meetings และ rooms เพื่อสรุปออกมาเป็นตารางเรียนประจำสัปดาห์ที่มีทั้งชื่อวิชา รหัสกลุ่ม รหัสห้อง และเวลาเรียน โดย Query ทั้งหมดใช้เวลาไม่ถึง 1 มิลลิวินาที

Q4: โครงการนี้อยู่บน Cloud จริงหรือแค่จำลองในเครื่อง?

ตอบ: อยู่บนระบบคลาวด์จริง 100% ครับ โดยฐานข้อมูล Cloudflare D1 โฮสต์อยู่ที่ศูนย์ข้อมูลสิงคโปร์/กรุงเทพฯ (APAC) และตัว API Deploy อยู่บน Cloudflare Workers ที่ URL https://timetable-room-api.6731503021.workers.dev ซึ่งสามารถเปิดทดสอบผ่านอินเทอร์เน็ตได้ตลอด 24 ชั่วโมง
